## Проблема масштабирования vector search

Хотя keyword и semantic search формируют основу production retriever, при масштабировании этих техник возникают новые проблемы. При наивной реализации vector search масштабируется особенно плохо, требуя значительных вычислительных ресурсов и добавляя задержку (latency) в систему.

## K-Nearest Neighbors (KNN)

Простейшая форма векторного извлечения называется `k-nearest neighbor search` (поиск k ближайших соседей) — именно она использовалась на протяжении курса до сих пор.

Алгоритм:

1. Создаётся embedding-вектор для каждого документа в knowledge base, а также для промпта.
2. Вычисляется расстояние между вектором промпта и вектором каждого документа.
3. Документы сортируются по расстоянию от вектора промпта.
4. Пользователь может выбрать число `k` — сколько таких ближайших соседних документов вернуть.

`KNN` легко понять и легко реализовать. Проблема в том, что он ужасно плохо масштабируется: число вычислений, требуемых для каждого поиска, растёт линейно с числом документов в knowledge base.

- Если документов тысяча, для каждого поиска нужно вычислить тысячу векторных расстояний.
- Если документов миллиард, нужно вычислить миллиард векторных расстояний — и такой второй поиск будет в миллион раз медленнее первого.

Если нужен retriever, хорошо работающий при масштабировании, требуется более совершенный подход.

## Approximate Nearest Neighbors (ANN)

Чтобы улучшить KNN, retriever используют семейство алгоритмов, называемых `approximate nearest neighbors`, или `ANN`. Эти алгоритмы используют хитрые структуры данных, позволяющие значительно ускорить поиск. Для этого они идут на небольшую жертву в качестве результатов — то есть не гарантируют нахождение абсолютно ближайших документов в knowledge base, хотя всё равно найдут те, что находятся очень близко.

### Navigable Small World

Рассмотрим типичный ANN-алгоритм под названием `navigable small world`.

Ещё до выполнения какого-либо поиска алгоритм создаёт структуру данных, называемую `proximity graph` (граф близости):

1. Сначала вычисляется расстояние между каждым вектором и каждым другим вектором.
2. Внутри этого proximity graph добавляется по одному узлу (node) для каждого документа.
3. Наконец, создаётся ребро (edge) между каждым документом и несколькими другими документами, к которым он ближе всего.

В результате получается структура, похожая на паутину (web-like structure). Можно представить, что перемещение по proximity graph происходит путём «прыжков» от одного документа к его ближайшим соседям вдоль соединяющих их рёбер.

### Как proximity graph ускоряет поиск

Когда поступает промпт, он векторизуется, создавая query vector. Цель — найти документы, расположенные ближе всего к этому query vector. Для этого алгоритм:

1. Случайным образом выбирает начальную точку входа (entry point), называемую candidate vector — это просто один из узлов proximity graph. Это по-настоящему случайный выбор, без какого-либо предположения, что он близок к вектору промпта.
2. Начинает обход графа: смотрит на каждого соседа текущего candidate vector и вычисляет, какой из них ближе всего к query vector. Поскольку соседей немного, этот процесс очень быстрый. Тот сосед, что оказался ближе всего, становится новым candidate.
3. Процесс повторяется: на каждом candidate vector алгоритм смотрит, какой из соединённых соседних векторов ближе всего к query vector, и тот становится новым candidate.
4. Процесс продолжается до тех пор, пока ни один из соседей не окажется ближе текущего candidate — тогда candidate vector возвращается как результат.

С небольшими модификациями этот подход можно заставить возвращать несколько документов, но основная идея остаётся той же: происходит перемещение по proximity graph, каждый раз выбирая того соседа, который приближает к промпту.

Этот подход не обязательно находит наилучший из возможных векторов в knowledge base — где-то может существовать вектор, более близкий к вектору промпта, который просто не будет достигнут алгоритмом, поскольку он не может выбрать оптимальный общий путь через proximity graph — лишь наилучший путь в каждый момент. На практике, тем не менее, этот алгоритм находит очень близкие векторы, причём гораздо быстрее, чем k-nearest neighbors.

## Hierarchical Navigable Small World (HNSW)

Хотя navigable small world уже эффективнее KNN, небольшая вариация под названием `hierarchical navigable small world`, или `HNSW`, добавляет дополнительное улучшение, значительно ускоряя ранние этапы поиска.

HNSW опирается на наличие иерархического (hierarchical) proximity graph с несколькими слоями (layers). Вот как может выглядеть такой иерархический proximity graph для knowledge base с тысячей документов:

- **Слой 1 (Layer 1)** содержит все тысячу векторов, и proximity graph вычисляется как обычно.
- **Слой 2 (Layer 2)**: случайным образом отбрасываются все векторы, кроме 100, и для этих 100 векторов строится новый proximity graph.
- **Слой 3 (Layer 3)**: случайным образом отбрасываются все векторы, кроме 10, и снова строится proximity graph для оставшихся 10.

### Как выполняется поиск по такому графу

1. Поиск начинается в слое 3 — верхнем слое. Алгоритм выбирает случайную точку входа в этом слое и затем ищет как обычно, чтобы найти наилучшего кандидата в слое 3.
2. Затем алгоритм спускается в слой 2, начиная с наилучшего кандидата, найденного в слое 3. Поскольку здесь больше векторов, потенциально может найтись вектор, более близкий к вектору промпта. Алгоритм перемещается по слою 2 как обычно, пока не найдёт наилучшего кандидата в слое 2.
3. В этот момент алгоритм спускается в слой 1 — самый нижний уровень, который содержит каждый вектор в knowledge base. Алгоритм перемещается по этому нижнему слою как обычно, и на этот раз найденный наилучший кандидат — это то, что алгоритм фактически возвращает.

Такой иерархический подход очень эффективен, потому что на самых высоких слоях алгоритм совершает большие «прыжки», чтобы попасть в приблизительную окрестность вектора промпта. К тому моменту, когда рассматриваются какие-либо возможные векторы в слое 1, candidate vector уже должен быть очень близок к вектору промпта.

### Сложность HNSW

Этот алгоритм HNSW значительно быстрее, чем поиск k-nearest neighbor. По мере продвижения вверх по слоям количество векторов для навигации экспоненциально уменьшается, поэтому время выполнения HNSW приблизительно логарифмическое, тогда как у KNN оно линейное. Именно это позволяет vector search масштабироваться до миллиардов векторов, при этом требуя лишь нескольких сотен миллисекунд задержки.

## Ключевые выводы про ANN

Реализовывать такие ANN-алгоритмы самостоятельно не потребуется, но важно понимать несколько их ключевых особенностей:

1. Они значительно быстрее k-nearest neighbors, что позволяет vector search оставаться возможным при масштабировании.
2. Хотя они, как правило, находят документы, близкие к векторам промпта, они не могут гарантировать нахождение абсолютно наилучших совпадений.
3. Весь процесс зависит от построения хорошего proximity graph — довольно вычислительно затратного процесса, который, к счастью, может быть предварительно вычислен (pre-computed) до получения каких-либо промптов.

Это хорошее резюме того, как ANN-алгоритмы делают vector search возможным при масштабировании. Далее рассматриваются инструменты, которые используются для фактической реализации этих алгоритмов.
