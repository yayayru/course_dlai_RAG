## Зачем очищать промпты пользователя

Важный шаг в production RAG-системе — очистка (cleaning up) промптов, отправленных пользователем. RAG-системы часто разворачиваются в контекстах, где конечный пользователь ожидает взаимодействовать с LLM в разговорной манере, как будто общается с другим человеком. В результате написанные человеком промпты для LLM оказываются плохими поисковыми запросами.

Вместо того чтобы подавать такие промпты напрямую в vector database, retriever может разобрать (parse) промпт, чтобы определить его намерение (intent), и отредактировать, переписать или полностью трансформировать промпт, чтобы оптимизировать его для извлечения. Существует множество техник query parsing — далее рассматривается несколько из них.

## Query rewriting

Самое простое и, безусловно, наиболее широко используемое решение проблемы «неаккуратных» промптов — использовать LLM для переписывания запроса перед его отправкой в retriever.

Пример: рассмотрим RAG-систему, построенную вокруг knowledge base медицинской информации. Можно настроить LLM как query rewriter со следующим промптом:

> *«The following prompt was submitted by a user in order to query a database of medical documents linking symptoms to diagnoses. Rewrite the prompt to optimize it for searching the database by doing the following: Clarify ambiguous phrases, use medical terminology where applicable, add synonyms that increase the odds of finding matching documents, remove unnecessary or distracting information»* — и далее вставляется промпт пользователя.

Пациент мог бы отправить промпт: *«I was out walking my dog, a beautiful black lab named Poppy, when she raced away from me and yanked on her leash hard while I was holding it. Three days later, my shoulder is still numb and my fingers are all pins and needles. What's going on?»* Такой промпт явно не оптимизирован для извлечения.

Вот переписанный промпт после прохождения через query rewriter: *«Experience a sudden forceful pull on the shoulder resulting in persistent shoulder numbness and finger numbness for three days. What are the potential causes or diagnoses such as neuropathy or nerve impingement?»*

Новый промпт убирает ненужную информацию, проясняет неоднозначности и даже использует некоторую медицинскую терминологию, которая может повысить шансы найти совпадение в knowledge base.

Хотя над промптом для query rewriting можно и нужно итерировать, в целом получаемые от этого выгоды существенны и легко оправдывают дополнительные затраты на вызов LLM, необходимый для очистки каждого промпта.

## Более продвинутые техники

Хотя базовый query rewriting обычно единственная техника query parsing, которая потребуется, существуют и более продвинутые техники.

### Named Entity Recognition (NER)

`Named entity recognition` — техника распознавания категорий информации в запросе, таких как места, люди, даты, вымышленные персонажи и так далее. Эта информация затем может использоваться либо для того, чтобы направить vector search, выполняемый retriever, либо для metadata filtering, выполняемого позже в процессе.

Пример здесь — модель под названием **Gliner**, которая является моделью общего назначения для named entity recognition. Ей можно передать фрагмент текста, а затем список типов сущностей, которые нужно идентифицировать, например, люди или даты. Модель проанализирует запрос и вернёт размеченный (labeled) запрос с идентификациями этих категорий.

В конкретном примере в текст было передано указание модели Gliner попытаться пометить любые упоминания person, books, locations, dates, actors, characters. В ответе видно, что модель пометила каждое упоминание этих различных сущностей.

Это очень эффективная модель, и её можно запускать при каждом поступлении запроса; включение этого шага добавляет немного дополнительной задержки, но качество извлечения в результате может значительно улучшиться.

### Hypothetical Document Embeddings (HyDE)

Ещё одна продвинутая техника query parsing называется `hypothetical document embeddings`, или `HyDE`. Этот подход уточняет поисковый запрос, генерируя гипотетический документ (hypothetical document), который был бы идеальным результатом процесса поиска.

Например, применительно к более раннему медицинскому вопросу, LLM использовалась бы для генерации гипотетического документа о онемении плеча и руки в результате резкого рывка. Затем этот гипотетический документ векторизуется, и именно его векторное представление фактически используется для завершения поиска.

Идея здесь в том, чтобы помочь retriever понять не только намерение промпта или вопроса, но и то, как выглядел бы качественный результат. Обычно retriever должен сопоставлять промпты с документами, поэтому в некоторой степени retriever сопоставляет несхожие типы текста — «яблоки с апельсинами». Генерируя гипотетический документ, retriever теперь сравнивает более похожие тексты: гипотетический идеальный документ и документы, фактически содержащиеся в knowledge base.

На практике HyDE действительно даёт улучшения производительности, но ценой некоторой дополнительной задержки в поиске и вычислительных ресурсов, необходимых для запуска LLM, генерирующей гипотетические документы.

## Итог по query parsing

По опыту автора курса, наличие того или иного query parsing — ключевой элемент RAG-системы. Практически во всех случаях базовый query rewriting — то есть просто использование хорошо промптированной LLM для базовой «доводки» промптов пользователя — правильный подход. Более продвинутые техники, такие как named entity recognition, HyDE и другие, могут давать дополнительные преимущества, но они могут быть сложнее в реализации и не обязательно дают лучшие результаты. Стоит поэкспериментировать с этими продвинутыми техниками и позволить результатам определить, как должен развиваться проект.
