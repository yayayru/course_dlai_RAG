# Security

## Источники

- `10_lec_Security.trans.txt`
- Дополнительно: `RAG_M5.pdf` (слайды 56–62)

## Область рассмотрения

Кибербезопасность — глубокая и постоянно развивающаяся область, поэтому невозможно охватить каждый возможный риск безопасности. Вместо этого рассматриваются некоторые вызовы и возможности безопасности, уникальные для RAG-системы. Основной фокус — обеспечение безопасности информации в `knowledge base`.

## Почему knowledge base часто содержит приватные данные

Распространённая причина, по которой изначально выбирается построение RAG-системы, — наличие приватной или проприетарной информации. Эта информация намеренно держится за пределами открытого веба, где LLM с гораздо большей вероятностью была бы на ней обучена. Даже после построения RAG-системы, скорее всего, всё равно хочется сохранить эти данные приватными.

## Способы утечки информации из knowledge base

### 1. Прямой запрос через промпт

Пользователь может просто запросить информацию напрямую через отправленный промпт. Хорошо сформулированный промпт может убедить LLM напрямую процитировать информацию из извлечённых чанков knowledge base. Даже при наличии защитных мер (`safeguards`), разумно предполагать, что пользователи приложения могут по крайней мере косвенно получить доступ к содержимому knowledge base.

**Решения:**

- **Аутентификация пользователей** соответствующим образом, применительно к информации, к которой им разрешён доступ. Например, если knowledge base содержит приватные корпоративные данные, обеспечение того, чтобы промптить RAG-систему могли только залогиненные сотрудники, — хорошее начало.
- **Разделение данных по нескольким арендаторам (tenants)** на основе привилегий ролевого доступа (`role-based access`, `RBAC`). Иными словами, если промпт пользователя приводит к извлечению из `vector database`, пользователь теоретически должен иметь доступ только к документам, соответствующим его роли и уровню доступа.

  Теоретически можно хранить все документы в единственном арендаторе (`single tenant`) и использовать фильтры метаданных, чтобы определять, к каким документам должен иметь доступ пользователь, но на практике эта техника слишком подвержена сбоям. Фильтрация метаданных лучше всего подходит для персонализации, но не для безопасности. Для безопасности гораздо более надёжный подход — хранение нескольких раздельных арендаторов (`separately stored tenants`).

### 2. Утечка через провайдера LLM

Ещё один способ, которым данные knowledge base теоретически могут утечь, — если промпты отправляются провайдеру LLM для генерации завершений (`completions`). Augmented prompt, который отправляется, будет содержать документы или чанки извлечённого текста из knowledge base, и в этой точке контроль над безопасностью теряется. В зависимости от уровня безопасности информации в knowledge base, это может быть неприемлемым риском.

**Решение:** можно выбрать запуск RAG-системы полностью локально, on-premises. Это означает хостинг LLM и `vector database` на собственном оборудовании. Хотя это может внести дополнительную сложность и накладные расходы в проект, при этом появляется контроль над содержимым knowledge base на протяжении всего RAG pipeline. Если требуется одновременно развернуть RAG-систему и обеспечить высокий уровень безопасности для knowledge base, этот шаг переноса всей системы on-premises может того стоить.

### 3. Прямой взлом базы данных

Ещё один способ, которым knowledge base может быть скомпрометирован, — она может быть просто напрямую взломана (`hacked`), как это возможно с любой традиционной базой данных.

Один способ, которым традиционные базы данных защищаются от несанкционированного доступа, — шифрование (`encrypting`) своего содержимого. Это означает, что даже если хакер получит доступ к базе данных, он не сможет легко получить доступ к зашифрованной информации.

`Vector database` представляют некоторые уникальные вызовы для этого вектора атаки. Чтобы `ANN`-алгоритм мог работать, по крайней мере плотные векторные представления (`dense vector representations`) документов должны храниться в памяти в расшифрованном виде. Сам текст чанков, однако, может храниться и извлекаться в зашифрованном виде, а затем позже расшифровываться для построения augmented prompt.

Некоторые провайдеры `vector database` теперь предоставляют такой сервис, либо можно самостоятельно выбрать шифровать и расшифровывать чанки. Это добавляет дополнительную сложность и, возможно, некоторую задержку системе, но предоставляет дополнительный уровень безопасности.

### Риск реконструкции текста из плотных векторов

Те плотные векторы, которые должны оставаться расшифрованными, к сожалению, всё же могут представлять некоторые риски безопасности. Недавние исследования показали возможность реконструкции исходного текста из его плотных векторных представлений. Иными словами, даже если чанки зашифрованы, возможно, хакер сможет реконструировать их из незашифрованных плотных векторов.

В настоящее время исследуются некоторые техники для решения этой проблемы безопасности, такие как:

- добавление шума к плотным векторам;
- применение к ним трансформаций;
- уменьшение размерности таким образом, чтобы сохранить расстояния, но затемнить (`obscuring`) семантическое значение.

Каждая из этих техник добавляет сложность `retriever` и, как правило, снижает производительность системы.

Несколько уникальная потенциальная уязвимость безопасности `vector database` — предмет продолжающихся исследований, но стоит быть о ней осведомлённым. Эта атака требует, чтобы хакер одновременно получил прямой доступ к базе данных и использовал экспериментальные техники для реконструкции текста из плотных векторов, но представляет собой возможную угрозу безопасности.

## Итог

Это был краткий взгляд на безопасность RAG-системы, но, надеюсь, он помог подсветить проблемы, уникальные для RAG. Главный вывод здесь должен быть таким: нужно помнить, что knowledge base, скорее всего, содержит некоторую приватную информацию, и что необходимо понимать и контролировать, как эта информация доступна. Сочетание техник из этого видео с более широким набором мер предосторожности в кибербезопасности должно помочь улучшить безопасность production RAG-системы.
