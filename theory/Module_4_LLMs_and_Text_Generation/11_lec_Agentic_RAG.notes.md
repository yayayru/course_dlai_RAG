## Идея агентных workflow

По мере того как RAG-система развивается, мощный способ улучшить её производительность — начать внедрять агентные workflow (`agentic workflows`). `Agentic workflow` означает использование нескольких LLM на протяжении всей RAG-системы, каждая из которых отвечает за один шаг общего процесса.

Эта идея уже встречалась ранее — с LLM, используемыми для выполнения таких задач, как расширение запроса (`query expansion`), переписывание промпта (`prompt rewriting`) или генерация цитат (`citation generation`). Существует огромное множество составных систем (`compound systems`) такого рода, которые можно построить.

## Два основных изменения в агентной системе

Обычно способ использования языковой модели — подать ей промпт, и она выдаёт ответ. Просто. В агентной системе в эту модель вносятся два основных изменения:

1. **Задачи как серия шагов и решений.** Задачи теперь рассматриваются как серия шагов и решений, каждый из которых может быть выполнен вызовом другой LLM.
2. **Доступ к более широкому набору инструментов.** LLM получают доступ к более широкому набору инструментов (`tools`), таких как интерпретатор кода (`code interpreter`), веб-браузер, или, в случае RAG, `vector database` с информацией для обращения.

## Пример агентной RAG-системы

Рассматривается один из возможных агентных workflow для RAG-системы:

1. Пользователь отправляет промпт в систему, и он сначала обрабатывается небольшой LLM-маршрутизатором (`router LLM`). Задача этой LLM — определить, действительно ли промпт требует обращения к vector database. Она специально настроена для этой задачи и выдаёт только `yes` (промпт оправдывает извлечение из базы данных) или `no` (на промпт можно ответить без извлечения).
2. В зависимости от решения `router LLM`, промпт либо отправляется в vector database для извлечения, либо пропускает этот шаг.
   - Если извлечение не выполняется, промпт отправляется напрямую в отдельную LLM для генерации ответа.
   - Если шаг извлечения был запрошен, используется отдельная LLM-оценщик (`evaluator LLM`), чтобы определить, достаточны ли извлечённые документы для ответа на вопрос. На основе решения этой LLM-оценщика могут быть запрошены дополнительные извлечения из vector database.
3. Как только достаточно информации извлечено, конструируется augmented prompt и передаётся LLM для генерации ответа.
4. На этом этапе финальная LLM проходит по этому ответу и добавляет цитаты.

Это лишь одна возможная агентная RAG-система, но она подсвечивает несколько ключевых моментов, верных для любой агентной системы.

## Ключевые принципы агентных систем

### Агентные системы как flowchart

Проектирование агентной системы по сути можно представлять как рисование блок-схемы (`flowchart`). Каждая LLM в диаграмме по-прежнему просто принимает текстовый ввод и генерирует текстовый вывод, но система устроена так, что каждая LLM выполняет одну задачу на пути промпта через RAG-систему.

### Разные LLM для разных задач

Не нужно использовать одну и ту же LLM для каждого шага в workflow. `Router` и `evaluator` LLM в этой агентной системе могли бы быть лёгкими (lightweight) моделями, быстрыми и дешёвыми в эксплуатации, поскольку у них единственная и относительно простая задача. Затем можно использовать более крупную модель для генерации черновика ответа и выбрать модель, специализирующуюся на генерации цитат для этого шага.

## Распространённые паттерны агентных workflow

При добавлении агентных workflow в RAG-приложение стоит рассмотреть несколько распространённых паттернов:

- **Sequential workflow (последовательный workflow)** — просто перемещает вывод линейным образом через серию LLM. Это может означать, что каждый промпт, отправленный в систему, проходит через LLM-парсер запроса (`query parser`), переписывающую запрос LLM (`query rewriter`) и LLM-генератор цитат как часть процесса генерации. Каждая LLM просто фокусируется на одном шаге общего процесса и поэтому может специализироваться на этом шаге.
- **Conditional workflow (условный workflow)** — использует LLM, чтобы решить, каким из многих путей должен следовать промпт. Только что был показан пример, где `router LLM` реализует такой workflow, решая, требуется ли извлечение для ответа на промпт. Также можно использовать маршрутизатор, чтобы определить, какая из нескольких LLM с разными сильными сторонами и специализациями должна использоваться для генерации ответа.
- **Iterative workflow (итеративный workflow)** — работает похоже на условный workflow, но направляет промпт обратно на более раннюю точку общей системы, формируя цикл (loop). Например, если RAG-система спроектирована для генерации кода, интегрирующегося с существующей кодовой базой, возможно, системе потребуется несколько попыток, чтобы написать рабочий код. LLM-оценщик может использоваться для оценки каждого черновика, возможно, с помощью интерпретатора кода, и предоставлять обратную связь, пока не сочтёт решение подходящим.
- **Parallel workflow (параллельный workflow)** — позволяет создать систему, в которой языковая модель-оркестратор (`orchestrator`) разбивает промпт на несколько отдельных задач и назначает каждую задачу отдельной LLM. На другом конце языковая модель-синтезатор (`synthesizer`) объединяет их работу. Например, если приложение сравнивает ключевые инсайты из двух научных статей, может понадобиться, чтобы две разные LLM суммировали и оценивали каждую статью, а затем оркестратор объединял их выводы.

## Реализация агентных систем

Для простых агентных систем можно просто самостоятельно реализовать логику желаемого workflow. По мере усложнения систем, однако, существует широкий спектр инструментов, библиотек и платформ, спроектированных, чтобы помочь строить и управлять агентной системой.

## Итог

Творческие возможности при построении агентных систем поистине безграничны. Здесь также присутствует важный сдвиг мышления: LLM начинают выглядеть чуть менее как самостоятельные решения и больше как модульные элементы, которые встраиваются в более крупный workflow. Внезапно становится вполне комфортно использовать более маленькие модели или модели, которые отлично справляются лишь с несколькими задачами, поскольку их возможности хорошо согласуются с той частью workflow, за которую они отвечают. Добавление агентных компонентов может дать гибкость для построения ещё более способных RAG-систем.
