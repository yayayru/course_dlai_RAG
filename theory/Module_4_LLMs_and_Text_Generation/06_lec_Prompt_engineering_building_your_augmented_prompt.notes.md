# Prompt engineering: building your augmented prompt

- Дополнительно: `RAG_M4.pdf` (слайды 39–47)

## Зачем нужен prompt engineering

Чтобы получить максимум от `LLM`, требуется написать качественный промпт. `Prompt engineering` — общий (umbrella) термин для набора техник промптинга, которые обычно ведут к более качественным результатам. Далее рассматривается несколько техник prompt engineering и то, как их можно использовать для улучшения общей производительности RAG-системы.

## Формат messages

Для начала полезно понять, как промпты фактически строятся в коде. Наиболее распространённый формат — формат сообщений OpenAI (`messages format`), который структурирует промпты как серию сообщений с использованием простой JSON-структуры.

Одно сообщение имеет:

- **content** — просто текст сообщения;
- **role** — роль, которая может быть `system`, `user` или `assistant`.

Роли:

- **System** — сообщения, предоставляемые LLM, чтобы влиять на её общее поведение; обычно включают высокоуровневые инструкции.
- **User** — сообщения, фиксирующие промпты, уже отправленные пользователем системы.
- **Assistant** — сообщения, фиксирующие ответы, ранее сгенерированные LLM.

### Многоходовой разговор (multi-turn conversation)

Когда с LLM ведётся продолжительный разговор туда-сюда (`multi-turn conversation`), LLM на самом деле не «помнит» сказанное ранее. Вместо этого за кулисами весь разговор конвертируется в этот формат messages, новое сообщение пользователя добавляется в конец, и весь разговор целиком отправляется в LLM при каждом новом промпте пользователя.

JSON-объект messages затем превращается в единую текстовую строку, которую может обработать LLM. Эта строка шаблона чата (`chat template string`) использует специальные текстовые теги, такие как стрелки или вертикальные черты, чтобы обозначить начало и конец каждого сообщения. LLM обучены распознавать эти теги и понимать разницу между системными, пользовательскими и ассистентскими сообщениями.

Этот формат очень гибкий и позволяет добавлять в промпты широкий спектр контекста, чтобы помочь контролировать, как отвечает LLM.

## System prompt

Первое, что нужно сделать при конструировании промпта для RAG-системы — написать `system prompt`. Он даёт LLM высокоуровневые инструкции о том, как ей следует себя вести. Если нужно, чтобы LLM всегда говорила в определённом тоне или следовала определённым процедурам, эта информация должна идти в system prompt.

Чтобы получить представление о том, что может входить в system prompt, в лекции рассматривается system prompt от популярного LLM-чатбота. Первое, что бросается в глаза — это его длина: он огромен. Не всегда нужно писать system prompt на несколько страниц, но полезно помнить, что такая гибкость есть.

В начале такого промпта обычно присутствует информация о дате отсечения обучения (`knowledge cutoff`) модели, а также текущая дата. Подобная информация помогает LLM определить, насколько устарела её информация и в состоянии ли она хорошо отвечать на определённые вопросы.

Более поздние разделы направляют LLM в отношении процесса и тона, который следует использовать при ответе на промпт. Например, они могут просить модель рассуждать над ответами шаг за шагом, не помогать с потенциально вредными запросами, отвечать в markdown. LLM также может быть сказано, что она интеллектуально любопытна и любит слышать, что думают об этом люди, вовлекаясь в обсуждение широкого спектра тем — это придаёт LLM определённую «личность», так сказать.

Эти же принципы можно использовать для конструирования собственного system prompt:

- можно дать LLM указание отвечать очень подробно, либо отвечать на вопросы кратко;
- поскольку system prompt конструируется для RAG-приложения, можно указать языковой модели использовать только извлечённые документы для ответа на промпты, оценивать релевантность документа или цитировать источники в своём ответе.

`system prompt` обычно добавляется к каждому промпту, который будет обрабатывать LLM, поэтому уделение времени его доработке — отличный способ улучшить стиль и качество результатов, которые в конечном итоге генерирует RAG-система.

## Построение augmented prompt

На этом этапе можно приступать к построению `augmented prompt`. Этот промпт потенциально включает множество частей информации, поэтому полезно построить хорошо продуманный шаблон промпта (`prompt template`).

Шаблон задаёт высокоуровневую структуру промпта и помогает решить, куда будут вставляться те или иные фрагменты содержимого. Например, можно всегда начинать с высокоуровневого system prompt, дающего высокоуровневые указания системе о том, как ей вести себя.

- Если система поддерживает многоходовые разговоры, можно включить предыдущие сообщения, отправленные между пользователем и LLM.
- Далее можно добавить топ-5 или топ-10 чанков, извлечённых `retriever`, а также любую информацию о том, как их обрабатывать.
- Наконец, можно включить самый последний промпт пользователя, на который LLM должна ответить.

Использование такого шаблона удобно тем, что оно упрощает экспериментирование с разными структурами промпта: можно изменять отдельные компоненты общего промпта и смотреть, как это влияет на итоговый сгенерированный ответ.

Так выглядит построение типичного промпта в RAG-системе, объединяющего хорошо написанный system prompt, извлечённый контекст, детали предыдущего разговора и, конечно, самый последний промпт пользователя.
